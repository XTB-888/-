# FableLens（寓言透镜）落地实战手册

> 目标：从 0 到 1 做出“上传现实物品照片 → 自动生成寓言故事 + 连续绘本插图”的可演示项目。  
> 方式：按 **12 个步骤**推进，每一步都有明确产物与验收标准。

---

## 0. 先定义 MVP（第 0 天）

在开始写代码前，先把范围收敛到可完成版本：

- 输入：1 张物品图片 + 1 个故事风格（治愈/冒险/暗黑）。
- 输出：
  - 500~800 字中文寓言故事；
  - 4 页分镜脚本；
  - 4 张风格一致、角色一致的插图。
- 约束：单次生成控制在 60~120 秒内。

**验收标准**
- 你能在一次演示中稳定跑通上传 → 故事 → 图片全链路。

---

## 1. 技术选型与目录搭建（第 1 天）

建议先分成两个工程：

```txt
fablelens/
  frontend/    # Next.js 14
  backend/     # FastAPI + LangGraph
  docs/        # 设计文档与 Prompt
```

### 1.1 前端初始化

- Next.js 14（App Router）
- Tailwind CSS + shadcn/ui
- Zustand（管理任务状态）

### 1.2 后端初始化

- FastAPI
- LangChain + LangGraph
- ChromaDB
- 对接模型网关（Ollama / OpenAI-compatible API）

**验收标准**
- `frontend` 能启动并展示上传页面。
- `backend` 能启动并暴露 `/health` 接口。

---

## 2. 设计核心数据结构（第 1~2 天）

先定义统一 JSON 契约，避免后续返工。

```json
{
  "item_name": "旧雨伞",
  "visual_features": ["黑色", "布面磨损", "木柄", "边缘有补丁"],
  "personality_traits": ["沉稳", "忠诚", "有点固执"],
  "story_character_hint": "像一个守护者",
  "style": "治愈",
  "outline": {
    "theme": "陪伴与成长",
    "pages": [
      {"page": 1, "scene": "雨夜街角", "plot": "..."}
    ]
  }
}
```

建议建这几个 Pydantic 模型：

- `VisionAnalysis`
- `StoryOutline`
- `StoryboardPage`
- `GenerationTask`

**验收标准**
- 任一模块都使用同一套 schema，接口文档自动生成（FastAPI /docs 可见）。

---

## 3. 先做“视觉理解模块”（第 2~3 天）

目标：上传图片后拿到结构化角色设定。

### 3.1 Prompt 模板（关键）

让模型必须输出 JSON，且字段固定：

- `item_name`
- `visual_features`
- `personality_traits`
- `story_character_hint`

### 3.2 工程要点

- 图片统一缩放到固定边长（如 768）。
- 增加 JSON 修复器（防止模型多说废话导致解析失败）。
- 给出 fallback：若性格推断失败，使用规则模板补齐。

**验收标准**
- 用 10 张不同照片测试，结构化字段解析成功率 > 90%。

---

## 4. 构建 RAG 故事模板库（第 3~4 天）

你要准备一个小型“寓言母本库”：

- 每条模板包含：主题、冲突类型、情绪弧线、结局类型、适用风格。
- 初期准备 50~100 条就够用。

### 4.1 文档切分建议

把每条模板存成独立 JSON 或 Markdown 块，字段化存储，便于过滤检索。

### 4.2 向量检索策略

- 向量查询文本由 `item_name + personality_traits + style` 拼接。
- TopK=5，按风格做 metadata filter。
- 结果重排：优先冲突类型多样化，避免生成套路过同质。

**验收标准**
- 同一输入多次检索能返回“相关且不重复”的模板。

---

## 5. 微调/替代方案（二选一）（第 4~7 天）

### 路线 A：LoRA 微调（加分高）

- 基座：Qwen2-7B-Instruct
- 数据：200~1000 条“寓言风格样本（输入画像→输出故事）”
- 输出目标：语言风格更统一、更文学化。

### 路线 B：不微调，先做强 Prompt（更快）

- 用 few-shot + 风格约束 + 结构化大纲生成。
- 面试时说明“已预留 LoRA 插槽”。

> 建议：先 B 跑通闭环，再 A 升级。

**验收标准**
- 生成故事有明确起承转合，且角色设定与图片特征一致。

---

## 6. 故事生成链路（第 7~8 天）

将文本生成拆成两段，质量更稳：

1. `OutlineChain`：先生成 4 页分镜大纲（每页：场景、冲突、情绪、旁白要点）
2. `NarrativeChain`：按大纲扩写完整故事

### 6.1 强制约束

- 统一主角称谓（避免“伞先生/它/小伞”乱切）。
- 每页必须有“视觉可画元素”（便于后续出图）。

**验收标准**
- 任意结果可自动拆成 4 个 image prompt，且每段可视化描述充分。

---

## 7. 图像生成与角色一致性（第 8~10 天）

这是项目亮点。

### 7.1 最小可用方案

- SDXL + IP-Adapter（注入原图特征）
- 固定 style prompt（统一画风）
- 每页仅改变场景描述与动作描述

### 7.2 稳定策略

- 固定同一随机种子区间（可微调）。
- 对主角特征设置 `must-have tokens`（如“黑色旧雨伞、木柄、补丁边缘”）。
- 加一轮图像自检：用 VLM 回读图像，检查是否仍是同一角色。

**验收标准**
- 4 张图主角可被人类一眼识别为同一角色。

---

## 8. 用 LangGraph 串成工作流（第 10~11 天）

建议节点：

- `analyze_image`
- `retrieve_templates`
- `generate_outline`
- `generate_story`
- `generate_storyboards`
- `render_images`
- `quality_check`

加两条控制逻辑：

- 若 `quality_check` 失败 → 回到 `generate_storyboards` 重试。
- 若图像失败次数超过阈值 → 返回“仅文本结果 + 重试建议”。

**验收标准**
- 工作流状态可追踪（每个节点耗时、输出摘要、错误信息）。

---

## 9. 前端交互实现（第 11~12 天）

页面分 3 个区域：

- 左侧：上传区 + 风格选择 + 生成按钮
- 中间：流式故事文本
- 右侧：绘本画廊（4 页）

建议体验细节：

- 任务进度条（视觉理解→检索→写作→出图）
- 失败可重试某一步（不必重跑全流程）
- 导出 PDF（加分项）

**验收标准**
- 非技术用户能在 1 分钟内理解并完成一次生成。

---

## 10. 评估体系与面试话术（第 12~13 天）

你至少要有 3 类指标：

1. **文本质量**：完整性、寓意清晰度、风格一致性
2. **图像质量**：角色一致性、构图可读性、风格统一度
3. **系统性能**：端到端时延、成功率、重试率

可做一个小评测集（30 张图片），生成后人工打分。

**验收标准**
- 你能拿出“可量化结果”，而非只展示 demo。

---

## 11. 部署上线（第 13~14 天）

推荐：

- 前端：Vercel
- 后端：Modal / AutoDL
- 对象存储：OSS / S3
- 向量库：本地 Chroma（早期）→ 云托管（后期）

上线前 checklist：

- 限流与鉴权（API Key / JWT）
- 异常日志与任务追踪
- 结果缓存（同图同风格可复用）

---

## 12. 你的两周执行计划（可直接照做）

- Day 1-2：脚手架 + schema + 图片上传
- Day 3-4：VLM 结构化输出
- Day 5-6：RAG 库 + 检索
- Day 7-8：故事生成链
- Day 9-10：SDXL + IP-Adapter 连续出图
- Day 11：LangGraph 串联 + 重试
- Day 12：前端联调
- Day 13：评测与优化
- Day 14：部署 + Demo 视频录制

---

## 你可以马上开始的第一个里程碑（今天）

今天只做三件事：

1. 跑起 `frontend` 和 `backend` 空项目。
2. 做一个 `/api/vision/analyze` 假接口（先返回 mock JSON）。
3. 前端完成上传 + 调接口 + 显示 JSON。

当这一步完成，你就已经有了“真实可见”的项目雏形。接下来每个模块都可以替换成真模型，不会空中楼阁。

---

## 常见坑（提前避雷）

- 一开始就追求“超长故事 + 超多页”会拖垮速度，先做 4 页。
- 不做结构化 schema，后续模块必然互相打架。
- 图像一致性别只靠 prompt，必须引入 IP-Adapter/参考图机制。
- 不记录中间结果，出了问题无法定位是检索错、写作错还是出图错。

---

## 最后：面试时怎么讲（30 秒版本）

“我做了一个多模态绘本生成系统。用户上传现实物品照片后，我先用 VLM 提取物体语义和角色性格，再通过 RAG 检索寓言模板，结合微调/约束生成分镜故事，最后用 SDXL + IP-Adapter 生成保持角色一致性的多页插图。底层用 FastAPI + LangGraph 编排全流程，前端是 Next.js 流式展示。我还做了评测集来量化文本质量、角色一致性和端到端时延。”

这段话基本能覆盖面试官最关心的：多模态、RAG、微调、Agent、工程落地。
